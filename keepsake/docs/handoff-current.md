- October 18: measured on the owner's PC (RTX 3070, Edge, 1080p): the room holds 60 fps at rest in both qualities with about 5x headroom, but froze for 2.1 s right after the loading screen hid, and for 70 to 220 ms when a view first showed an object. Cause: on Windows the browser's graphics layer builds the real GPU program on a shader's first draw, so compiling behind the loading screen was not enough. `ShaderWarmup` now draws one object per shader program into a scissored pixel before the gate opens, and `LateShaderGuard` does the same for late objects. Separately, every click re-rendered the whole app and room three times (about 75 React commits) because the autosave status lived in the app context; it is now a small external store (`src/store/saveStatus.ts`) and the context value is memoised. Measured again on the same PC (PR #29): the room now appears already responsive at about 4.7 s instead of appearing at 2.0 s and freezing for 2.3 to 2.5 s; looking around no longer hitches (longest frame 216 → 17 ms); the loading bar never steps backwards. A fourth commit halves the shader count: the Canvas's bare `shadows` prop asked for the soft shadow type, which three.js r185 swaps for `PCFShadowMap` on the first shadow pass, so every program was built twice; the Canvas now names `shadows="percentage"` (38 → 20 programs). Measured on the same PC against the base build: the room responds to clicks at 5.4 s instead of 6.5 to 8.0 s, the longest freeze during load is 0.11 s instead of 1.9 to 2.8 s, camera drag 17 ms instead of 167 to 250 ms. Still open: the remaining driver linking for 20 programs behind the loading screen (fewer lights would shorten it) and a 33 to 50 ms frame on Season → Winter, probably a texture uploading on first use. The room assets from PRs #27 and #28 did not change the render cost.
